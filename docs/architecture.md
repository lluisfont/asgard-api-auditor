# Architecture

## Purpose

`asgard-api-auditor` is a producer of verified API/integration knowledge. It is intentionally separate from the central knowledge repository/RAG.

## Components

```text
repository snapshot
      |
      v
[inventory]
  files / languages / frameworks / integration libraries
      |
      v
[discovery]
  exposed routes
  outbound HTTP calls
  other integration surfaces
      |
      v
[analysis]
  normalize
  classify
  attach evidence
  resolve provider/consumer when supported
      |
      v
[coverage]
  detector executions
  unsupported patterns
  failed scans
  inventory completeness
      |
      +-------------------+
      |                   |
      v                   v
[openapi]             [knowledge]
openapi.yaml          api-knowledge.md
      |                   |
      +---------+---------+
                |
                v
          findings.json
          audit-report.md
                |
                v
         [publication]
         atomic publish
```

## Source of truth

The audited source repository at an exact commit is the primary evidence. Generated artifacts are derived knowledge and must always record that commit.

## OpenAPI standard

HTTP contracts generated by this project use **OpenAPI 3.1.2**.

OpenAPI is not used to hide unsupported integration types. GraphQL, WebSocket, gRPC, SOAP, SSE and other surfaces are recorded in `findings.json` and `api-knowledge.md` even when they cannot be represented by the generated OpenAPI document.

## Stable identity

The system uses stable identifiers so audits can be compared safely:

- `audit_id`: unique execution identifier.
- `repository_id`: normalized repository identity.
- `api_id`: stable logical API identity when resolvable.
- `endpoint_id`: stable endpoint identity derived from API/direction/method/normalized path.
- `detector_id` + `detector_version`: exact detector implementation used.

IDs are not inferred from display names alone when ambiguity exists.

## Detector architecture

Detectors implement narrow responsibilities and produce normalized findings. Examples:

- Laravel/PHP route detector;
- PHP cURL/Guzzle consumer detector;
- JavaScript Axios/Fetch detector;
- Flutter/Dart HTTP/Dio detector;
- environment/config URL detector;
- OpenAPI/Swagger existing-spec detector.

Each detector must declare:

- supported patterns;
- unsupported patterns;
- version;
- confidence rules;
- evidence emitted;
- coverage category;
- failure behavior.

## Cross-repository correlation

Provider-consumer correlation is not assumed from names alone. Prefer, in descending strength:

1. exact base URL + normalized path;
2. service/domain configuration + path;
3. explicit SDK/client reference;
4. runtime/test evidence;
5. inference marked `probable` or `unverified`.

## Publication model

Candidate artifacts are generated in staging. They are validated together and published as one logical audit. If validation or publication fails, the previous valid audit remains intact.

## Future API gate

The same engine can compare the contract reconstructed from a PR with the previous approved contract, detect breaking changes and query `asgard-api-knowledge` for affected consumers before merge.
