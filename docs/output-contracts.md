# Output Contracts

## Shared metadata

All four primary outputs must carry or visibly state:

- `schema_version`;
- `audit_id`;
- `auditor_version`;
- `repository`;
- `source_ref`;
- `source_commit`;
- `audit_timestamp`.

## `findings.json`

Canonical structured result for automation and cross-repository correlation.

It contains:

- coverage;
- HTTP endpoints exposed and consumed;
- request/response contract details;
- response fields actually consumed;
- authentication;
- evidence;
- other integration surfaces;
- unresolved items;
- comparison/breaking-change data when available;
- hashes/status of sibling artifacts.

Schema: [`../schemas/findings.schema.json`](../schemas/findings.schema.json).

## `correlations.json`

Canonical structured result for deterministic provider-consumer relationships generated by:

```bash
asgard-api-auditor correlate \
  --findings repo-a/findings.json \
  --findings repo-b/findings.json \
  --output correlation-results
```

Correlation reads versioned `findings.json` artifacts. It does not rescan repositories and does not couple repository scanners together.

The v0.6.0 correlation key is strictly:

```text
HTTP method + normalized path shape
```

Only route parameter names are normalized. Literal path segments, nesting depth, HTTP method and trailing slash semantics remain distinct.

Each consumed HTTP endpoint receives exactly one status:

- `matched_confirmed`: explicit provider identity evidence exists in the consumer finding and selects a matching provider endpoint.
- `matched_unique_candidate`: exactly one provider endpoint shares the same method and normalized shape, without independent provider proof.
- `ambiguous`: more than one provider endpoint shares the same method and normalized shape.
- `unmatched`: no provider endpoint shares the same method and normalized shape.

Unique candidates are not confirmed dependencies. The artifact also includes `provider_reverse_index`, split into confirmed, unique-candidate and ambiguous consumer references so provider-side impact queries do not overstate certainty.

Schema: [`../schemas/correlations.schema.json`](../schemas/correlations.schema.json).

## `api-relations.md`

RAG-ready Markdown generated beside `correlations.json`.

It summarizes input snapshot provenance, coverage, provider relationship sections, unmatched consumers and ambiguous consumers. It must not introduce stronger claims than `correlations.json`; in particular, unique structural matches remain candidate relationships.

## `openapi.yaml`

OpenAPI 3.1.2 representation of sufficiently verified exposed HTTP APIs.

Required traceability extensions should use the `x-asgard-` prefix, for example:

```yaml
x-asgard-audit-id: audit-...
x-asgard-source-commit: abc123...
x-asgard-endpoint-id: api::GET::/path
```

OpenAPI does not represent the complete repository integration inventory; consumed APIs and unsupported/non-HTTP surfaces remain in findings/knowledge.

## `api-knowledge.md`

RAG-oriented semantic representation. It must not introduce claims absent from `findings.json` or other cited evidence.

Every endpoint section must include its stable endpoint ID and evidence summary.

## `audit-report.md`

Human-facing audit result including:

- verdict/status;
- source snapshot;
- coverage;
- detector limitations/failures;
- summary counts;
- breaking changes since previous audit;
- unresolved items;
- security-sensitive findings by reference without exposing secrets.

## Cross-output consistency

A candidate audit set is invalid if repository, commit, audit ID or auditor version differ across outputs.

Correlation artifacts are generated as a separate atomic set: `correlations.json` and `api-relations.md` must be published together or not at all.

## `api-catalog.json`

Canonical v0.8 API catalog generated from a validated `findings.json` artifact:

```bash
asgard-api-auditor catalog-api \
  --findings audit-output/findings.json \
  --output api-catalog.json
```

The catalog preserves endpoint direction (`exposed` or `consumed`) and source evidence. Endpoint identity is derived from intrinsic contract identity only: direction, method, path shape and an explicit stable namespace when supplied. `api_id` is a grouping field and is not an endpoint identity input.

Schema: [`../schemas/api-catalog.schema.json`](../schemas/api-catalog.schema.json).

## `api-compatibility.json`

Reference/candidate compatibility report generated by:

```bash
asgard-api-auditor compare-api \
  reference-api-catalog.json \
  candidate-api-catalog.json \
  --output api-compatibility-output
```

Classifications are `same`, `additive`, `breaking` and `unknown`. Material unknown facts remain `unknown`, including self-comparison; `observed_equal` and `artifact_equal` are separate equality observations and do not imply compatibility.

By default, every reference endpoint inside the selected scope is a required compatibility requirement. Explicit include/exclude selectors are recorded in scope metadata.

Schema: [`../schemas/api-compatibility.schema.json`](../schemas/api-compatibility.schema.json).

## `consumer-compatibility.json`

Provider/consumer compatibility report generated by:

```bash
asgard-api-auditor check-consumer-compatibility \
  --consumer-catalog consumer-api-catalog.json \
  --provider-catalog provider-api-catalog.json \
  --output consumer-compatibility-output
```

Provider/consumer compatibility is directional. The provider must accept every request shape the consumer can produce and must produce the response fields/statuses the consumer proves it needs. Every consumed endpoint inside the selected scope is a required dependency unless explicitly excluded.

Schema: [`../schemas/consumer-compatibility.schema.json`](../schemas/consumer-compatibility.schema.json).
